# Архитектура MVP

Цель — не сделать "второй Notion", а сделать **движок принятия решений**, который из обычных заметок строит карту проблем, целей и действий.

Главное правило MVP:

> **Минимум сущностей, максимум автоматизации.**

* * *

# Почему это MVP

* **Простая модель данных** — всего 7 таблиц.
* **SQLite** не требует отдельного сервера БД.
* **FastAPI** быстро поднимает REST API.
* **LLM используется только для извлечения сущностей** (проблем, целей, действий и связей), а вся логика приоритизации реализуется локально, что снижает стоимость и делает поведение системы предсказуемым.
* **Граф зависимостей строится в памяти** (например, через словари или библиотеку `networkx`), без необходимости использовать Neo4j или другую графовую БД.

## Возможности после MVP

Эта архитектура легко расширяется без переписывания ядра:

* добавление векторного поиска для похожих заметок (`ChromaDB` или `FAISS`);
* хранение истории изменений и прогресса по проблемам и действиям;
* автоматическое объединение дублирующихся проблем и целей;
* прогнозирование влияния новых действий на уже существующий граф;
* персональные правила приоритизации (например, здоровье всегда важнее финансов);
* визуализация графа проблем, целей и действий.

Такой подход позволяет за несколько недель собрать рабочий прототип, используя практически полностью бесплатный стек, а затем постепенно наращивать интеллектуальные возможности без смены архитектуры.

## Я бы вообще разделил систему на три слоя

### 1. LLM (понимание текста)

Только отвечает на вопрос:

> Что человек сейчас сказал?

Возвращает структурированный JSON.

* * *

### 2. Python (логика)

Работает с базой:

* объединяет одинаковые сущности;
* считает связи;
* обновляет статистику;
* строит граф;
* пересчитывает приоритеты.

* * *

### 3. Recommendation Engine (аналитика)

Уже отвечает на вопросы:

* что является первопричиной большинства проблем;
* какое действие устранит максимальное число последствий;
* какие привычки чаще всего коррелируют с продуктивностью;
* какие инсайты регулярно подтверждаются наблюдениями.

Именно такое разделение делает систему простой, дешевой в эксплуатации и масштабируемой: LLM используется только там, где нужен смысл текста, а вся накопительная "интеллектуальность" формируется обычной логикой Python на основе сохраненных данных.

## Самая сильная часть системы — объединение графа и векторов

Допустим пользователь спрашивает:

> Почему у меня последние две недели падает продуктивность?

Система делает так:

1. **Векторный поиск** — находит все похожие заметки про продуктивность, сон, дедлайны, концентрацию.
2. **Граф** — строит цепочку причинно-следственных связей между найденными сущностями.
3. **LLM** — на основе найденного формулирует понятный вывод.

Например:

> За последние 14 дней в 9 из 11 заметок встречается связка:
> 
> YouTube вечером → поздний сон → плохой сон → низкая концентрация → перенос задач.

Это уже не просто поиск по заметкам, а аналитика.

## Для MVP этого достаточно

Не нужны сложные нейросети или графовые базы. Можно использовать:

* **SQLite** — хранение сущностей и связей;
* **NetworkX** — работа с графом в памяти;
* **ChromaDB** или **FAISS** — бесплатная векторная база;
* **OpenAI** или локальная модель через Ollama — извлечение смысла.

Такая архитектура остается простой, но при этом позволяет постепенно превращать обычные заметки в систему, которая накапливает знания о пользователе и начинает выявлять закономерности, а не просто хранить текст.

## Есть еще вариант, который мне нравится больше

Вообще отказаться от отдельной векторной БД на старте.

Хранить **эмбеддинг каждой заметки прямо в SQLite** (например, как массив или BLOB). При появлении новой заметки Python вычисляет эмбеддинг и сравнивает его с уже существующими (через косинусное сходство). Пока заметок меньше примерно **10–30 тысяч**, это будет работать достаточно быстро и без дополнительной инфраструктуры.

Получается такой путь развития:

1. **MVP** — SQLite + граф.
2. **Версия 1.5** — те же SQLite + граф, но с эмбеддингами в SQLite для семантического поиска.
3. **Когда данных станет много** — заменить хранение эмбеддингов на FAISS или ChromaDB практически без изменения остальной архитектуры.

Такой подход сохраняет MVP максимально простым, но не закрывает путь к более умному поиску и аналитике в будущем.
