## 1. Полный pipeline обработки данных

### Схема цепочки

```
Пользователь
  │ POST /webhook/v3-pipeline {"text": "...", "source": "..."}
  ▼
┌── n8n (оркестратор) ──────────────────────────────────────────┐
│                                                                │
│  Шаг 1: POST /v3/process                                       │
│         → v3-api: insert_note(text, source)                    │
│         → SHA256 хеш, дедупликация по hash                     │
│         → Возвращает: {"status":"ok", "note_id": N}            │
│         ▼                                                      │
│  Шаг 2: POST /v3/graph/sync                                    │
│         → v3-api: sync_graph_to_pg()                           │
│           → LightRAG: get_all_labels() → список меток          │
│           → LightRAG: get_graph(label, depth=3) для каждой     │
│           → upsert_entity() + insert_relation() в PG            │
│         → Возвращает: {"entities_count": N, "relations_count": M}│
│         ▼                                                      │
│  Шаг 3: POST /v3/priority/compute                              │
│         → v3-api: compute_priorities()                         │
│           → Читает все entities, relations, actions из PG       │
│           → Word overlap + fuzzy matching описаний с сущностями │
│           → Вычисляет impact_score, priority_score             │
│           → Обновляет actions в PG                              │
│         → Возвращает: {"actions_updated": N}                   │
│         ▼                                                      │
│  Шаг 4: GET /v3/priority/top?limit=5                           │
│         → v3-api: топ действий по priority_score               │
│         → Возвращает: {"actions": [...]}                       │
│         ▼                                                      │
│  [Шаг 5: Code-нода форматирования — ВЫРЕЗАНА (нет Python)]     │
│                                                                │
│  (Параллельно, не связано с основным потоком)                  │
│  PG: Entities → SELECT ... ORDER BY importance DESC LIMIT 10   │
│  PG: Actions  → SELECT ... ORDER BY priority_score DESC LIMIT 10│
└────────────────────────────────────────────────────────────────┘
  │
  ▼
Пользователь: JSON с top-5 actions
```

### Анализ каждого этапа

| Этап | Вход | Что делает | Выход | Потери данных | Создаёт |
|------|------|-----------|-------|--------------|---------|
| **1. Process Note** | `{text, source}` | SHA256-хеш, INSERT в `notes` | `{note_id}` | Нет | 1 запись в notes |
| **2. Sync Graph** | `note_id` (не используется) | GET /labels → GET /graph для каждой → upsert | `{entities_count, relations_count}` | **Связь заметка→сущность не сохраняется** | N entities + M relations |
| **3. Compute Priority** | Все entities, relations, actions | Word/fuzzy matching | `{actions_updated}` | Нет | Обновляет priority_score |
| **4. Top Actions** | `limit` | SELECT с сортировкой | `{actions: [...]}` | **Нет контекста - только цифры** | Временный JSON |

### Критические проблемы pipeline

1. **Потеря связи «заметка → сущность»**: entities и relations не имеют `note_id`. Нельзя узнать, из какой заметки пришла сущность.

2. **Нет инкрементальной синхронизации**: каждый вызов `/v3/graph/sync` заново запрашивает **все** метки и **все** графы у LightRAG, даже если добавилась только одна заметка. O(n) HTTP-вызовов к LightRAG.

3. **actions не создаются pipeline-ом**: функция `upsert_action()` существует, но **никем не вызывается**. Действия должны быть предварительно загружены в БД — автоматического извлечения действий из заметок нет.

4. **Observations не используются**: таблица `observations` создаётся, но никогда не заполняется.

5. **Шаги 1-4 можно объединить**: вместо 4 отдельных HTTP-вызовов из n8n, можно сделать один эндпоинт `/v3/pipeline` в v3-api.

6. **Все сущности загружаются в память**: `get_all_entities()`, `get_all_relations()`, `get_all_actions()` без пагинации.

## 2. Разделение ответственности

### LightRAG

| Аспект | Оценка |
|--------|--------|
| **Делает свою работу?** | ✅ Да: эмбеддинги (bge-m3), построение графа, RAG-запросы |
| **Делает чужую работу?** | ⚠️ Нет, но качество графа полностью зависит от LLM (qwen2.5:1.5b) |
| **Чего не хватает?** | Нет доступа к промптам (шаблоны в `prompts/`), нет кастомных инструкций для выделения сущностей |
| **Лишняя логика?** | Нет |

LightRAG — правильный выбор для RAG-компонента. Проблема в LLM: **qwen2.5:1.5b** — маленькая модель (1.5B параметров). Для качественного извлечения сущностей и построения графа знаний на русском языке рекомендуется модель 7B+.

### v3-api

| Аспект | Оценка |
|--------|--------|
| **Делает свою работу?** | ⚠️ Частично |
| **Делает чужую работу?** | **Да**: дублирует функции оркестрации (n8n делает то же самое) |
| **Чего не хватает?** | Нет сквозного pipeline-эндпоинта, нет обработки ошибок, нет очередей |
| **Лишняя логика?** | Priority Engine можно вынести в отдельный сервис |

v3-api выполняет **три разнородные функции**: API-прокси к LightRAG, синхронизация графа, вычисление приоритетов. Это нарушает Single Responsibility Principle.

### PostgreSQL

| Аспект | Оценка |
|--------|--------|
| **Делает свою работу?** | ✅ Как хранилище — да |
| **Делает чужую работу?** | Нет |
| **Чего не хватает?** | **pgvector не используется** — векторный поиск только внутри LightRAG |
| **Лишняя логика?** | Нет |

### Graph Builder

| Аспект | Оценка |
|--------|--------|
| **Нужен ли?** | ⚠️ Спорно |
| **Дублирует ли LLM?** | Нет |
| **Дублирует ли Python?** | Нет |
| **Что делает не так?** | Просто копирует данные LightRAG → PG без трансформации |

Graph Builder нужен **только если** в PG выполняются аналитические запросы, которые LightRAG не умеет (агрегации, JOIN-ы, временные ряды). Если аналитика делается через LightRAG — Graph Builder избыточен.

### n8n

| Аспект | Оценка |
|--------|--------|
| **Нужен ли?** | ⚠️ Спорно |
| **Что делает?** | 4 последовательных HTTP-вызова |
| **Можно убрать?** | **Да** — заменить на один эндпоинт `/v3/pipeline` в v3-api |
| **Лишняя сложность?** | Да — добавляет точку отказа, сложность деплоя, зависимость |

n8n оправдан, если пайплайн будут настраивать бизнес-пользователи через UI. Если разработчик — проще и надёжнее встроить пайплайн в v3-api.

## 3. Извлечение данных

### Текущее состояние

| Тип данных | Кто извлекает | Статус |
|-----------|--------------|--------|
| **Сущности** | LightRAG (автоматически) | ✅ Работает |
| **Связи** | LightRAG (автоматически) | ✅ Работает |
| **Наблюдения** | Никто | ❌ Таблица мертва |
| **Проблемы** | Никто | ❌ Не извлекаются |
| **Решения** | Никто | ❌ Не извлекаются |
| **Действия** | Ручной ввод в БД | ❌ Не автоматизировано |
| **События** | Никто | ❌ Не извлекаются |
| **Привычки** | Никто | ❌ Не извлекаются |
| **Эмоции** | Никто | ❌ Не извлекаются |
| **Цели** | Никто | ❌ Не извлекаются |
| **Проекты** | Никто | ❌ Не извлекаются |

### Критические проблемы

1. **LightRAG с qwen2.5:1.5b не может качественно извлекать семантические типы** — он выделяет сущности, но не различает проблему, решение, эмоцию, цель. Нужен либо более мощный LLM, либо отдельный Python-парсер с NLP.

2. **Действия не извлекаются из текста** — они должны либо автоматически выводиться из проблем (например, "проблема X → нужно сделать Y"), либо задаваться пользователем.

3. **Нет извлечения временных данных** — когда произошло событие, как часто повторяется, в какой последовательности.

4. **Нет разметки тональности** — эмоциональная окраска не определяется.

### Что нужно изменить

- Добавить Python-слой NLP перед LightRAG для первичного выделения типов сущностей
- Дополнить LightRAG кастомными промптами для русскоязычного извлечения
- Реализовать автоматическое создание actions через LLM
- Добавить временные метки к событиям

## 4. Аналитика

### Что текущая архитектура может вычислить

| Аналитика | Возможность | Механизм |
|-----------|-------------|----------|
| Самые важные проблемы | ⚠️ Частично | Entity importance (веса связей) |
| Приоритет задач | ✅✅ | Priority Engine (score 0-495+) |
| Самые связанные сущности | ⚠️ Частично | Сумма входящих/исходящих весов |
| Топ действий | ✅ | `/v3/priority/top` |

### Что НЕ может вычислить

| Аналитика | Почему невозможно |
|-----------|------------------|
| **Повторяющиеся проблемы** | Нет идентификации «проблема» как типа сущности |
| **Причины проблем** | Нет связей `cause → effect` |
| **Последствия проблем** | Нет связей `problem → consequence` |
| **Закономерности** | Нет механизма поиска паттернов во времени |
| **Триггеры** | Нет событийной модели |
| **Успешные/неудачные решения** | Нет обратной связи, нет оценки результата |
| **Корреляции между сущностями** | Нет аналитических SQL-запросов с корреляцией |
| **Влияние действий на результат** | Нет цикла «действие → результат → оценка» |
| **Эффективность решений** | Нет метрик effectiveness |
| **Изменение состояния во времени** | **Нет временной размерности** в entities |
| **Самые дорогие проблемы** | Нет метрики cost/impact |
| **Ключевые точки роста** | Нет прогнозирования |
| **Источники стресса** | Нет эмоциональной аналитики |
| **Полезные привычки** | Нет трекинга привычек |

### Коренная причина

Текущая архитектура не разделяет **сущности по семантическим типам**. Всё — просто "entity" с полем `type`, которое заполняет LightRAG как попало. Для аналитики нужно чёткое разделение:

```
Person → имеет → Problem
Problem → имеет → Cause
Problem → требует → Action
Action → приводит → Result
Person → практикует → Habit
Habit → влияет → Emotion
Person → ставит → Goal
Goal → состоит из → Project
```

Без этой модели любая аналитика будет поверхностной.

## 5. Приоритизация

### Текущий алгоритм

```
Для каждого action:
  Для каждой entity:
    Если слова описания пересекаются со словами имени entity:
      match_score = (importance + out_weight + in_weight) * overlap
      impact += match_score
  priority = impact * 10 + hits * 5
```

### Что может

- Поставить **самый высокий приоритет** действию, которое упоминает много важных сущностей
- Учесть **вес связей** сущности (outgoing + incoming)

### Что НЕ может

| Аспект | Почему |
|--------|--------|
| **Блокировки** (A блокирует B) | Нет связей `blocks` |
| **Рычаги** (одно действие решает много задач) | Нет связей `action → solves → problem` |
| **Срочность vs важность** | Нет временных меток действий |
| **Каскадный эффект** | Нет графа зависимостей |
| **Затраты vs выгода** | Нет числовых метрик у действий |

### Что нужно добавить

1. Определить действия как **тип сущности**, а не отдельную таблицу
2. Добавить связи `action → entity` (FK) вместо word matching
3. Добавить типы связей: `blocks`, `enables`, `solves`, `causes`
4. Реализовать **топологическую сортировку** для обнаружения блокировок
5. Добавить весовые коэффициенты для типа связи

## 6. Связи

### Текущая модель

```
Entity ──relation_type──→ Entity
  (relation_type = 'related' по умолчанию)
  (weight = 1 по умолчанию)
```

Типы связей, которые LightRAG может генерировать: **не определены** — всё идёт с типом `related`.

### Эталонная модель (что должно быть)

| Связь | Тип | Семантика |
|-------|-----|-----------|
| Problem → Cause | `causes` | Проблема A является причиной B |
| Problem → Solution | `solved_by` | Проблема решается действием/решением |
| Solution → Action | `requires` | Решение требует конкретного действия |
| Action → Result | `results_in` | Действие приводит к результату |
| Person → Habit | `practices` | Человек практикует привычку |
| Habit → Emotion | `triggers` | Привычка вызывает эмоцию |
| Goal → Project | `decomposes_to` | Цель раскладывается на проекты |
| Observation → Problem | `indicates` | Наблюдение указывает на проблему |
| Problem → Emotion | `causes_emotion` | Проблема вызывает эмоцию |
| Action → Habit | `reinforces` | Действие укрепляет привычку |
| Solution → Effect | `produces` | Решение производит эффект |
| Action → Action | `blocks` / `enables` | Одно действие блокирует/разблокирует другое |

### Критическое замечание

LightRAG строит **свой собственный граф знаний** внутри себя. v3-api синхронизирует его в PG, но теряет все типы связей — они переименовываются в `related`. Graph Builder **не использует** типы связей из LightRAG.

```python
# graph_builder.py, строка ~27
db.insert_relation(e_from, e_to, weight=1, rtype="related")
```

Это делает всю синхронизацию графа почти бесполезной для семантической аналитики.

## 7. Graph Builder

### Текущая реализация (`graph_builder.py`)

```python
async def sync_graph_to_pg():
    labels = await get_all_labels()
    for label in labels:
        graph = await get_graph(label, max_depth=DEFAULT_DEPTH)
        for src, dst, data in graph:
            if src in SKIP or dst in SKIP:
                continue
            e_from = db.upsert_entity(...)
            e_to = db.upsert_entity(...)
            db.insert_relation(e_from, e_to, weight=1, rtype="related")
    return {"entities_count": ..., "relations_count": ...}
```

### Оценка

| Аспект | Оценка | Комментарий |
|--------|--------|-------------|
| Нужен ли? | ⚠️ Спорно | Если аналитика только через LightRAG — не нужен |
| Должен ли работать поверх LightRAG? | ✅ Да | LightRAG — единственный источник графа |
| Какие данные получает? | Список меток + графы из LightRAG | Полезная нагрузка ~50-200 КБ |
| Какие данные создаёт? | entities + relations в PG | **Теряет типы связей** (все → 'related') |
| Какие связи строит? | Только `related` | Не использует relation_type из LightRAG |
| Дублирует ли работу LLM? | Нет | LLM внутри LightRAG уже всё сделал |
| Дублирует ли работу Python? | Нет | Утилитарная функция |

### Проблемы

1. **Все связи типа `related`** — семантическая информация потеряна
2. **Нет фильтрации** — синхронизируются даже технические сущности (`<source_entity>`, `sin`, `cos`)
3. **Нет маппинга** — LightRAG использует один набор названий, PG — другой, но маппинг не настраивается
4. **Устаревшая глубина**: `max_depth=3` может быть мала или велика для разных типов сущностей

## 8. PostgreSQL

### Модель хранения

| Таблица | Нормализация | Связи | Индексы | Проблемы |
|---------|-------------|-------|---------|----------|
| **notes** | ✅ 3НФ | → observations | hash, (нет FK) | UNIQUE(hash) мешает хронологии |
| **entities** | ⚠️ 2НФ | → relations (FK) | type, name, LOWER(name) | **Нет note_id** — не привязаны к заметкам |
| **relations** | ✅ | → entities | Нет | Нет индекса на relation_type |
| **actions** | ✅ | Нет FK | Нет | **Нет связи с entities** |
| **observations** | ✅ | → notes | Нет | **Таблица мертва** — никто не пишет |

### Оценка

| Критерий | Оценка | Комментарий |
|----------|--------|-------------|
| Нормализация | ⚠️ 3НФ, но неполная | Нет типизации сущностей |
| Связи | ❌ Слабые | Отсутствуют FK между actions и entities |
| Индексы | ❌ Недостаточно | Нет составных индексов для аналитики |
| pgvector | ❌ Не используется | Образ pgvector, но векторы только в LightRAG |
| Масштабируемость | ❌ | Все SELECT без пагинации |
| Аналитика SQL | ❌ | Нет материализованных представлений, нет агрегаций |

### Рекомендации

1. Добавить `note_id FK` в `entities` для трассировки заметка→сущность
2. Создать таблицу `entity_types` (problem, solution, cause, emotion, ...) и FK в `entities`
3. Заменить word-matching в Priority Engine на FK `action_id → entity_id`
4. Использовать pgvector для хранения эмбеддингов сущностей в PG (чтобы не ходить в LightRAG)
5. Добавить составные индексы: `(type, importance)`, `(note_id, created_at)`
6. Убрать UNIQUE(hash) из notes, если нужна хронология повторных заметок
7. Добавить `updated_at` в actions

## 9. Масштабирование

### Сценарий: 100 000 заметок, 5 млн сущностей, 50 млн связей

| Компонент | Узкое место | Почему |
|-----------|-------------|--------|
| **get_all_entities()** | 💀 **Падение** | Загружает 5 млн строк в память |
| **get_graph(label)** | 💀 **Падение** | LightRAG не рассчитан на миллионы сущностей в оперативной памяти |
| **Priority Engine** | 💀 **Не выполнится** | O(A×E) = 5 млн действий × 5 млн сущностей |
| **sync_graph_to_pg()** | 💀 **Часы** | Каждую из 100k заметок синхронизировать через 3 вызова к LightRAG |
| **n8n** | ⚠️ Медленно | Каждый шаг — отдельный HTTP-вызов |
| **PostgreSQL** | ⚠️ Медленно | SELECT без пагинации, нет шардирования |
| **LightRAG** | ⚠️ Тяжело | Всё в json-файлах, нет шардирования |

### Что сломается первым

1. **Priority Engine** — O(n²) алгоритм упадёт при тысячах entities/actions
2. **get_all_entities()** — MemoryError в Python при миллионах записей
3. **sync_graph_to_pg()** — LightRAG будет отвечать минутами на каждый запрос

### Когда потребуется переработка

| Нагрузка | Действие |
|----------|----------|
| >1000 заметок | Добавить пагинацию во все SELECT |
| >10 000 entities | Priority Engine нужно переписать на SQL |
| >100 000 entities | Добавить фоновые задачи/очереди для sync |
| >1 млн entities | LightRAG → замена на Milvus/Qdrant/Weaviate |
| >10 млн relations | Шардирование PostgreSQL |

| **Priority Engine** | 5 | O(n²); word-matching вместо FK; нет блокировок | Переписать через SQL + FK |
| **Graph Builder** | 3 | Теряет типы связей; нет фильтрации | Использовать relation_type |
| **LightRAG** | 6 | qwen2.5:1.5b мал для русского; нет доступа к промптам | Увеличить LLM до 7B+ |
| **PostgreSQL** | 4 | Нет FK связей; pgvector не используется; слабые индексы | Доработать схему |
| **Извлечение данных** | 2 | Извлекаются только сущности; observations мертва | Добавить типизацию + NLP |
| **Аналитика** | 2 | Нет временных рядов, корреляций, паттернов | Добавить семантическую модель |
| **Масштабирование** | 2 | Не готово к росту | Пагинация, очереди, индексы |

### Критические ошибки

1. **Все типы связей → `related`** — Graph Builder теряет семантику при синхронизации. Граф в PostgreSQL бесполезен для аналитики.

2. **actions создаются вручную** — функция `upsert_action()` существует, но никогда не вызывается. Pipeline не создаёт действий.

3. **observations не заполняется** — таблица создана, но никто в неё не пишет.

4. **Нет связи заметка→сущность** — `entities` не имеют `note_id`. Нельзя отследить, из какой заметки пришла сущность.

5. **Priority Engine использует word-matching вместо FK** — алгоритм O(n²) и семантически бедный.

### Потенциальные проблемы в будущем

1. **qwen2.5:1.5b** слишком мал для качественного извлечения сущностей на русском языке (особенно тонких семантических различий)
2. LightRAG хранит всё в JSON-файлах — нет шардирования, нет репликации
3. n8n добавляет точку отказа: если n8n упал, pipeline не работает
4. Все endpoint-ы v3-api синхронные — блокируют друг друга при параллельных запросах
5. Нет мониторинга, нет логирования ошибок, нет метрик

### Рекомендации по упрощению архитектуры

1. **Убрать n8n** — заменить на эндпоинт `/v3/pipeline` в v3-api, который выполняет все 4 шага последовательно. Один HTTP-вызов вместо 4.

2. **Убрать дублирующие сервисы** — если parser и notes-api делают то же, что v3-api, выпилить их из docker-compose.

3. **Объединить Priority Engine с графом** — убрать word-matching, добавить FK `action_entity` и вычислять приоритет через SQL.

4. **Graph Builder → ETL-процесс** — переписать как фоновую задачу с фильтрацией и маппингом типов.

### Рекомендации по улучшению аналитики

1. **Добавить семантическую модель** — типы сущностей: `person`, `problem`, `solution`, `cause`, `emotion`, `goal`, `project`, `habit`, `event`, `observation`.

2. **Добавить временные ряды** — каждая сущность должна иметь `created_at` и `updated_at`, связи — тоже. Добавить таблицу `timeline`.

3. **Добавить FK между action и entity** — убрать word-matching, заменить на явные связи.

4. **Реализовать граф зависимостей** — типы связей: `blocks`, `enables`, `solves`, `causes`, `triggers`.

5. **Добавить обратную связь** — пользователь должен иметь возможность оценить, помогло ли действие. `action_feedback(action_id, rating, comment)`.

6. **Реализовать аналитические SQL-запросы** — корреляции, частотный анализ, топ-N по типам.

### Рекомендации по улучшению качества извлечения данных

1. **Заменить qwen2.5:1.5b на qwen2.5:7b** или другую 7B+ модель для русского языка (Saiga, YandexGPT API).

2. **Добавить Python-NLP слой** перед отправкой в LightRAG: spaCy или Natasha для первичного выделения именованных сущностей (NER) на русском.

3. **Настроить кастомные промпты LightRAG** для русского языка и семантической типизации: указать LLM, какие типы сущностей выделять.

4. **Убрать технические сущности** — `<source_entity>`, `<target_entity>`, односложные слова (`type`, `name`, `language`).

5. **Автоматическое создание actions через LLM** — после выделения проблем, LLM предлагает действия для их решения. Пример промпта:
   > "На основе следующих проблем: {список проблем}. Предложи 3-5 действий для их решения."

### Рекомендации по масштабированию

1. **Пагинация** — все `get_all_*()` функции должны принимать `limit` и `offset`
2. **Фоновые задачи** — sync_graph должен выполняться асинхронно через очередь
3. **Пакетная вставка** — заменить одиночные INSERT на `execute_values()` или `COPY`
4. **Составные индексы** — `(type, importance)`, `(from_entity_id, relation_type)`
5. **Кэширование** — закешировать результаты LightRAG (labels, graph) в Redis
6. **Шардирование** — на горизонте 10M+ записей, готовить partition by entity type
