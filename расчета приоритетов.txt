# Архитектурная задача: разработать систему накопительной аналитики и расчета приоритетов

## Контекст проекта

Мы создаем интеллектуальную систему заметок, которая должна не просто хранить текст пользователя, а постепенно строить граф знаний, анализировать закономерности и вычислять реальные жизненные приоритеты.

Это НЕ todo-приложение.

Это персональная аналитическая система ("второй мозг"), которая с каждой новой заметкой становится умнее.

Поэтому все решения необходимо принимать исходя из принципа накопления знаний.

---

# Главный принцип

Исходные данные никогда не удаляются.

Удаляться или пересчитываться могут только производные данные.

Необходимо разделить систему на три уровня.

---

# Уровень 1. История (Source of Truth)

Этот слой является источником истины.

Он содержит реальные события жизни пользователя.

Никогда не удаляется автоматически.

Содержит:

* notes
* entities
* relations
* observations
* actions

Каждая запись обязательно имеет:

* id
* note_id
* created_at
* source

Все данные должны быть восстановимыми.

Любая аналитика должна иметь возможность полностью пересчитаться только по этим данным.

---

# Уровень 2. Аналитика

Этот слой рассчитывается автоматически.

Он не хранит историю.

Он хранит агрегированную статистику.

Например:

entity_stats

* entity_id
* mentions_count
* notes_count
* first_seen
* last_seen
* trend
* importance
* priority

relation_stats

* relation_id
* mentions_count
* confidence
* correlation
* trend

category_stats

* category
* problems_count
* actions_count
* average_importance
* average_priority

Этот слой можно полностью удалить и построить заново.

---

# Уровень 3. Кэш

Этот слой хранит только готовые результаты.

Например:

* priorities
* recommendations
* dashboard
* top problems
* top actions

Он не является источником данных.

---

# Категории

Каждая заметка должна автоматически получать категорию.

Минимальный список:

* Здоровье
* Работа
* Финансы
* Отношения
* Психология
* Привычки
* Обучение
* Проекты
* Быт
* Другое

Каждая сущность должна принадлежать одной или нескольким категориям.

---

# Базовые веса категорий

Категория должна иметь стартовый вес.

Пример:

Здоровье = 100

Безопасность = 95

Финансы = 80

Работа = 75

Отношения = 70

Психология = 65

Обучение = 60

Проекты = 55

Быт = 40

Хобби = 25

Это стартовый коэффициент.

Он не определяет итоговый приоритет.

---

# Вес сущностей

Каждая новая сущность получает базовый вес.

Например:

Плохой сон

базовый вес = 30

Боль

базовый вес = 40

Прокрастинация

базовый вес = 20

Недостаток денег

базовый вес = 35

Далее этот вес изменяется аналитикой.

---

# Формула importance

importance не должно быть фиксированным числом.

Оно должно рассчитываться.

Пример компонентов:

importance =
+
базовый вес категории
+
базовый вес сущности
+
частота появления
+
давность последнего появления
+
длительность существования проблемы
+
эмоциональная интенсивность
+
количество связанных проблем
+
количество связанных решений
+
сила связей в графе
+
подтверждение пользователем

Каждый коэффициент должен иметь возможность изменяться без изменения архитектуры.

---

# Повторения

Повторения являются одним из самых важных факторов.

Пример:

01.07

Плохо спал

03.07

Плохо спал

07.07

Плохо спал

Это НЕ три одинаковые записи.

Это три подтверждения одной проблемы.

Следовательно:

растет importance

растет priority

растет уверенность системы

---

# Relations

Relations являются историей.

Каждая relation должна содержать:

relation_id

note_id

source_entity

target_entity

relation_type

confidence

created_at

Нельзя хранить только одну relation.

Необходимо хранить все подтверждения появления связи.

При этом агрегированная аналитика должна считать:

сколько раз появилась связь

в скольких заметках появилась

когда появилась впервые

когда появилась последний раз

насколько она устойчива

насколько высокая корреляция

---

# Граф

Граф должен постоянно объединять знания.

Например

Сегодня

Купить монитор

никаких выводов нет.

Через неделю появляется

Болят глаза

Через месяц

Работаю за компьютером по 12 часов

Граф должен самостоятельно установить цепочку

Монитор

↓

Компьютер

↓

Работа

↓

Нагрузка на глаза

↓

Боль

После этого действие

Купить монитор

автоматически становится более важным, потому что теперь оно потенциально решает несколько проблем одновременно.

---

# Действия

Каждое действие должно иметь возможность быть:

автоматическим

ручным

предложенным системой

Все действия участвуют в аналитике.

Даже если действие пока не связано с сущностями.

Если позже появляются новые данные, система должна попытаться автоматически связать действие с графом.

Пример

Сегодня

Купить монитор

priority = низкий

Через месяц

Болят глаза

Работа за компьютером

Низкая продуктивность

Система автоматически связывает действие с несколькими проблемами.

priority увеличивается.

---

# Приоритет

Приоритет должен рассчитываться динамически.

Он зависит не только от importance.

Необходимо учитывать:

важность категории

важность сущности

повторяемость

свежесть проблемы

силу графовых связей

количество решаемых проблем

количество блокируемых проблем

количество зависимых действий

вероятность положительного эффекта

Таким образом одно действие может подняться в рейтинге, если оно решает сразу несколько важных проблем.

---

# Аналитика должна отвечать

Какие проблемы повторяются чаще всего?

Какие проблемы появились недавно?

Какие проблемы существуют дольше всего?

Какие действия решают сразу несколько проблем?

Какие категории ухудшаются?

Какие категории улучшаются?

Какие проблемы имеют максимальное влияние на остальные?

Какие действия имеют максимальный потенциальный эффект?

---

# Пересчет

При изменении заметки:

необходимо пересчитать только данные, связанные с этой заметкой;

обновить агрегированную аналитику;

обновить веса;

обновить приоритеты.

Полный пересчет всей базы допускается только как отдельная сервисная операция.

---

# Масштабируемость

Архитектура должна быть рассчитана на многолетнее накопление данных.

История должна храниться полностью.

Производные данные должны пересчитываться.

Алгоритмы расчета весов должны изменяться без изменения структуры базы данных.

---

# Цель

В результате должна получиться система, которая не просто хранит заметки, а постепенно строит персональную модель жизни пользователя.

Каждая новая заметка должна увеличивать объем знаний системы.

Каждая новая связь должна повышать качество аналитики.

Каждый новый алгоритм должен иметь возможность полностью пересчитать всю аналитику без потери истории.

Итоговая система должна уметь самостоятельно выявлять скрытые закономерности, определять реальные причины проблем, находить наиболее эффективные действия и автоматически пересчитывать их приоритет по мере накопления новых данных.
