Задача: переработать хранение и синхронизацию relations
Контекст проекта
Мы строим не обычное CRUD-приложение, а систему накопления знаний и аналитики по заметкам пользователя.
Каждая заметка является отдельным событием и никогда не должна терять свою историю.
Основная идея проекта:
	•	каждая заметка имеет уникальный note_id; 
	•	из заметки извлекаются сущности; 
	•	между сущностями строятся связи (relations); 
	•	аналитика работает по всей истории заметок, а не только по последней записи; 
	•	повторения сущностей и связей должны увеличивать их значимость; 
	•	приоритеты рассчитываются на основании накопленной статистики. 
Поэтому модель "очистить всю таблицу relations и записать заново" для данного проекта НЕ подходит.

Проблема
Сейчас sync_graph_to_pg() при каждом запуске просто добавляет новые relations.
В результате:
	•	появляются дубликаты; 
	•	вес сущностей искусственно растёт; 
	•	аналитика становится неверной; 
	•	невозможно определить, из какой заметки появилась связь; 
	•	невозможно корректно пересчитать одну изменённую заметку. 

Что необходимо сделать
Нужно полностью переработать модель хранения relations.
Каждая relation должна быть связана с конкретной заметкой.
Например:
relations
	•	id 
	•	note_id 
	•	source_entity_id 
	•	target_entity_id 
	•	relation_type 
	•	weight 
	•	created_at 
Таким образом одна и та же связь может встречаться несколько раз, но каждая запись будет иметь собственный note_id.
Пример:
note 15
Sleep → Fatigue
note 28
Sleep → Fatigue
note 39
Sleep → Fatigue
Это НЕ три одинаковые ошибки.
Это три подтверждения одной закономерности.
Именно количество подтверждений должно участвовать в аналитике.

Новый алгоритм работы
При обработке новой заметки:
	1.	сохранить заметку; 
	2.	получить её note_id; 
	3.	удалить только автоматически созданные relations этой заметки (если заметка была изменена); 
	4.	построить новые relations; 
	5.	сохранить их с этим note_id; 
	6.	обновить агрегированную аналитику. 
Запрещено удалять relations других заметок.

Если пользователь редактирует заметку
Необходимо выполнить:
DELETE FROM relations WHERE note_id = :current_note_id
После этого построить relations только для этой заметки.
Все остальные данные должны сохраниться.

Что должна использовать аналитика
Аналитика должна работать не по количеству строк в таблице, а по агрегированным данным.
Например:
Entity
Sleep
должна иметь показатели:
	•	mentions_count 
	•	notes_count 
	•	first_seen 
	•	last_seen 
	•	trend 
	•	importance 
	•	priority 
Аналогично для relations.
Например связь
Sleep → Fatigue
должна иметь:
	•	сколько раз встретилась; 
	•	в скольких заметках встретилась; 
	•	когда появилась впервые; 
	•	когда была замечена последний раз; 
	•	насколько стабильна; 
	•	насколько сильная корреляция. 

Важное требование
Relations являются историей.
История не должна уничтожаться.
Пересчитываться должна только агрегированная аналитика.
То есть архитектура должна выглядеть следующим образом:
notes ↓
entities ↓
relations (история)
↓
analytics (агрегированные показатели)
↓
priorities

Категории
Так как далее будет строиться аналитика по сферам жизни, каждая заметка должна иметь категорию.
Например:
	•	здоровье; 
	•	работа; 
	•	финансы; 
	•	отношения; 
	•	обучение; 
	•	привычки; 
	•	проекты; 
	•	психология; 
	•	другое. 
Relations также должны иметь возможность связываться с категорией через note_id.
Это позволит позже анализировать:
	•	проблемы внутри категории; 
	•	связи между категориями; 
	•	влияние одной категории на другую. 

Проверить после реализации
После внесения изменений необходимо проверить:
	1.	Повторная обработка одной и той же заметки не создаёт дубликатов. 
	2.	Изменение заметки обновляет только её relations. 
	3.	Удаление заметки удаляет только связанные с ней relations. 
	4.	Повторения одной связи в разных заметках увеличивают статистику, но не создают ложный рост веса. 
	5.	Аналитика корректно считает: 
	•	количество повторений; 
	•	частоту; 
	•	тренды; 
	•	важность; 
	•	корреляции; 
	•	приоритет. 
	6.	Все существующие функции проекта продолжают работать после изменения схемы. 

Ожидаемый результат
В результате должна получиться архитектура, в которой:
	•	каждая заметка является независимым источником данных; 
	•	relations становятся историей событий; 
	•	аналитика рассчитывается поверх истории; 
	•	приоритеты вычисляются по накопленной статистике; 
	•	система поддерживает долгосрочное накопление знаний без появления дубликатов и без искусственного роста весов.
